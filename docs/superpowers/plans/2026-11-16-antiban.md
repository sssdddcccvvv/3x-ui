# AntiBan Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One `antibanEnable` panel toggle that, when on, enforces a hardened, legitimate-looking VLESS+REALITY profile on saved inbounds/clients and on every generated share link / subscription (forced Vision flow, filled shortIds/serverNames, fingerprint pin, ML-KEM dropped for Mihomo).

**Architecture:** Settings plumbing follows the existing `defaultValueMap` + `entity.AllSetting` + `SettingService.GetX()` pattern. Enforcement lives in one exported function `service.ApplyAntiBan(inbound)` called from inbound/client save paths and from the sub link-generation path. Mihomo profiles get `support-x25519mlkem768=false` when the toggle is on (the #6803 switch behavior).

**Tech Stack:** Go (gin + gorm), React/TS frontend, existing random/logger utils.

**Spec:** `docs/superpowers/specs/2026-11-16-antiban-design.md`

## Global Constraints

- Toggle default OFF (`"antibanEnable": "false"`); toggle OFF ⇒ byte-identical behavior to upstream (existing tests, incl. `internal/sub/characterization_test.go`, must keep passing).
- Only protocol `vless` with stream `security=reality` and transport `tcp` is hardened; respect the inbound's DisableFlow flag exactly as `internal/sub/clash_service.go:485` does (`!inbound.DisableFlow`).
- Never break link generation: malformed Settings/StreamSettings JSON ⇒ return input unchanged + log; no panic, no user-facing error.
- Key name is exactly `antibanEnable`; flow value exactly `xtls-rprx-vision`; shortIds are 8-char lowercase hex.
- New UI strings added to `internal/web/translation/en-US.json` and `ru-RU.json` minimum (keys `pages.settings.antibanEnable`, `pages.settings.antibanEnableDesc`).
- Work on branch `antiban` off current main; commit after every task.

## Review Focus

- Inbound with `DisableFlow` set — AntiBan must NOT inject flow (expect: unchanged flow). Test in Task 2.
- Plain-TLS (non-REALITY) vless and other protocols (vmess/trojan) — untouched. Test in Task 2.
- Toggle off — no diff at all (characterization suite + explicit off test). Tests in Tasks 1–3.
- REALITY inbound whose `dest`/`target` is unparseable and `serverNames` empty — must not block saves with a hard error when toggle on but log clearly; only hard-error is "toggle on + reality + no serverNames derivable at link-generation time" → skip hardening that inbound with a log (spec: warn, not block). Test in Task 2.
- Sub generation for an old client created before the toggle (Flow empty in DB) — generated link must still carry `flow=xtls-rprx-vision` when toggle on. Test in Task 3.
